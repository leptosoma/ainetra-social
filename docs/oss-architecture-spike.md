# OSS Architecture Spike — Phase 5.5 / Phase 6

Date: 2026-09-25. Status: analysis complete; no dependency or application change. Decisions below mean **recommended for the named future phase**, not already installed or in production. Commercial/SaaS license notes are risk triage, not legal advice.

## Existing boundary and decision

Ainetra Social is Next.js 16 / React 19 with PostgreSQL/Prisma, a tenant-scoped `SocialAccount`, `ScheduledPost`, `PublishAttempt`, and an approval/version check in `src/features/publishing/service.ts`. `/calendar` is a server-rendered timeline, not a multi-view workspace. Upload currently buffers the whole file, caps video at 80 MiB by default, checks container signature but not video codec/dimensions, and stores through `StorageProvider` (currently local). Phase 5 image transformations already use Sharp. There is no external publishing adapter, resumable upload, video processor, or worker. These are repository observations, not claims about production readiness.

**Direction:** reuse FullCalendar Standard for the desktop calendar surface; build the Ainetra mobile task/capture surface with native browser primitives. Keep Ainetra's PostgreSQL domain authoritative. Make publishing vendor-neutral before connecting a provider. Pilot Postiz as a *possible* backend, but use a minimal native Meta adapter for the first production Instagram/Facebook path unless the Postiz pilot passes the legal, isolation, headless connection, failure, and operations gates below. Do not adopt Mixpost Lite as that backend: its free edition omits Instagram and API. Defer a new queue and resumable-upload service until measured need; keep Sharp; adopt FFmpeg tooling when video metadata/normalization enters scope.

### Calendar implementation direction (P5.5A)

Use only FullCalendar Standard plugins, loaded on the calendar route, for desktop day/week/month/year layout, event positioning and optional drag/drop. Its standard year views remove the need for Premium Scheduler; no resource view is required. The React component is compatible with the current React major. Keep a server-side Ainetra calendar projection from active plan items and scheduled posts; event IDs refer to Ainetra IDs, never library IDs. Render plain-language statuses with icon **and** text; colors are secondary. `eventClick` opens an Ainetra drawer/sheet; dragging makes an Ainetra mutation request only after membership, approval/version, timezone and conflict checks, and the UI must revert if rejected. FullCalendar's WAI-ARIA support is useful but custom event markup and keyboard drag alternatives require manual accessibility verification. On small screens, an Ainetra Today/3-day/Week list and a light Month overview should be the main experience; year is desktop overview. Use selective plugins and route loading to control client weight; measure the production bundle rather than assuming a size. [Standard views](https://fullcalendar.io/docs/plugin-index), [React](https://fullcalendar.io/docs/react), [accessibility](https://fullcalendar.io/docs/accessibility), [license](https://fullcalendar.io/license).

### Mobile capture direction (P5.5B)

Use responsive Next/React UI, native `<input type="file" accept="image/*" capture>` / video capture as a progressive enhancement, gallery fallback, mobile bottom navigation and accessible sheets/dialogs. File input `capture` behavior varies by browser, so test real iOS Safari and Android Chrome, permissions, cancellation, orientation, and interrupted uploads. A PWA is optional after field testing; no separate camera library or service is justified now. Keep upload authorization, tenant, size/type inspection, capture-request fulfilment and immutable-original semantics on the server. Never let browser-provided media tags become Business Brain facts.

## Publishing ownership and replacement (Phase 6)

`Ainetra content + approval + schedule intent + tenant → PublishingAdapter → NativeMetaAdapter (first production) / PostizAdapter (isolated pilot or later platform backend) / future NativeTikTokAdapter → platforms`.

Define the Ainetra-owned contract first: `connectAccount`/disconnect and capability lookup; `prepareMedia`; `submit` with immutable approved content snapshot, scheduled-post ID, platform/account mapping, version and idempotency key; `cancel`/reschedule; `getStatus`/reconcile; normalized result with provider post ID, URL, attempt ID, timestamps, retryable/permanent failure class and redacted diagnostics; webhook validation/mapping. Do not put Postiz integration IDs, post payloads or status enums into Ainetra domain rows except provider-reference mapping. Ainetra PostgreSQL owns approval, intent, account-to-business mapping, due time, attempts and final publication state. A publish command checks current approval/version and tenant atomically and records an outbox item before external work. A worker claims due work, submits once per logical idempotency key, records uncertain outcomes as *unknown* until provider reconciliation, and never treats export or an HTTP timeout as confirmed publication. External APIs can still duplicate after an ambiguous timeout; map provider IDs, query before retry where possible, and surface uncertain posts for operator review. Retrying the worker or receiving a webhook twice must not make a second Ainetra mutation. [Current Ainetra baseline](../src/features/publishing/service.ts), [Postiz API](https://docs.postiz.com/public-api/introduction).

**Postiz pilot gate:** on a disposable isolated instance, demonstrate account connection without exposing a second customer dashboard, per-business account scoping, media transfer with private access, one scheduled and one immediate Meta publish, cancellation and reschedule, failed/ambiguous submission, webhook event validation, status reconciliation after downtime, restore from independent backup, and acceptable operator load. Obtain written legal review of AGPL and commercial terms before any customer production use. Postiz's public docs state that publish webhooks exist but do not document a signature there; do not infer authenticity—prove a supported verification mechanism or treat webhook as a hint and query provider status. [Postiz API](https://docs.postiz.com/public-api/introduction), [webhook docs](https://docs.postiz.com/general/automations/webhooks), [self-host compose](https://docs.postiz.com/self-host/installation/docker-compose).

**One-platform-at-a-time replacement:** route by `(platform, socialAccountId, adapterVersion)`; retain existing scheduled jobs on their recorded adapter until drained or explicitly migrated; new Meta accounts/jobs may use `NativeMetaAdapter` while another platform uses `PostizAdapter`. Reconcile remote IDs before changing route, preserve historical attempt/audit rows, and support rollback to the previous adapter for *new* jobs only. Customer-facing calendar/approval/content models never change with the backend.

## Security and data boundary

- Tokens: store provider/social tokens only in a server-side encrypted secrets boundary with per-tenant ownership, restricted access, rotation/revocation and audit; never in client props, logs, plaintext Postiz mapping fields or calendar events. If Postiz is used, it will also hold platform tokens; treat its database as sensitive and minimize Ainetra access. OAuth `state` must be checked. [Postiz OAuth](https://docs.postiz.com/public-api/oauth).
- Media: Ainetra stores originals and accepted derivatives; transfer to publisher only for the intended account/post, with short-lived scoped access or explicit upload, retention/deletion rules and no public bucket URLs. Prevent cross-tenant reuse of storage keys. An external service does not become the media master.
- Webhooks: authenticate using documented signature/shared secret or independent provider lookup, verify tenant/account mapping, reject replay and stale/version-mismatched events, deduplicate by provider event/post ID. Postiz's published-webhook page advises idempotency but does not establish signature behavior. [Postiz webhooks](https://docs.postiz.com/general/automations/webhooks).
- Failure: rate limits, revoked tokens, expired sessions, provider outage, worker crash and delayed callbacks must lead to explicit pending/unknown/failed states, bounded retry, alerting and reconciliation; never silently mark published.
- Backups: Ainetra PostgreSQL and media storage are authoritative; if Postiz is piloted, independently back up its PostgreSQL, Redis/Temporal state as applicable, secrets, uploads and adapter mappings and rehearse restore. Do not point Postiz at Ainetra's domain schema. [Postiz self-host](https://docs.postiz.com/self-host/installation/docker-compose).

## Savings and outstanding decisions

Qualitative savings: FullCalendar avoids building and maintaining four calendar layouts plus event positioning/drag behavior; FFmpeg avoids custom format, probe and transcode logic; a successful Postiz pilot could avoid some platform-specific OAuth/publishing work, but may lose that advantage to legal review and operations. No credible person-day, percentage or cash saving can be stated without a measured implementation trial. The owned adapter/outbox/tenant/security work is required regardless of provider.

Before implementation, product/operations must decide whether an extra self-hosted publisher and its AGPL review are acceptable for a limited Postiz pilot, and which production hosting/storage boundary is intended. Phase 5.5 and Phase 6 task statuses remain unchanged. This note does not authorize installing or integrating any candidate.
