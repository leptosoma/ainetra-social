## Outcome and boundary

An authenticated, authorized Ainetra business user can start native Meta OAuth, return safely, see the Facebook Pages available to that Meta user and each eligible linked Instagram professional account, explicitly choose the desired asset(s), and connect/reconnect/disconnect them. Ainetra PostgreSQL owns the mapping and encrypted credential boundary. The connection does **not** publish, create a publish intent, call `PublishingAdapter.submit`, or make an existing scheduled post publishable by itself. Preserve P6-01 immutable snapshot, idempotency, and `UNKNOWN` semantics.

Use **Facebook Login + Instagram API with Facebook Login** for this focused path so Page and Page-linked Instagram assets can be discovered together. Do not silently substitute Instagram Login: it uses different scopes and does not require Page linkage. Do not fabricate an Instagram account when a Page has none. An Instagram personal account is ineligible. A Page without Instagram may still be selectable for Facebook, subject to verified permissions/tasks.

## OAuth and state flow

1. Start only from an authenticated session with server-checked business membership; require `OWNER` for connection changes unless existing product authorization explicitly grants members that power. Derive the business from membership, not an untrusted browser assertion. Use a fixed configured HTTPS redirect URI (localhost exception for development), an allowlisted post-flow return path, and only required scopes. Never use a client-supplied absolute redirect URL.
2. Generate a cryptographically random state, persist only its hash with business, user **and current session identity**, a short expiry, and one-time status. Bind the callback to the same live Ainetra session. Reject missing/mismatched/expired/consumed state before exchanging a code; atomically consume it so concurrent callbacks cannot both proceed. On provider denial/error, mark attempt failed and show a recoverable, sanitized message. A retry starts a new attempt.
3. Exchange the authorization code server-side with Meta using the configured app ID/secret and exact redirect URI; validate token app/validity, granted permissions and expiry using Meta's documented mechanism. Exchange for longer-lived user credential only if the chosen current Meta flow supports it; do not assume a fixed lifetime or perpetual Page token. Never send the code or token to client props, browser storage, URL redirects, logs, exception text, or telemetry. Limit provider timeouts and response size; do not turn partial results into `CONNECTED`.
4. Server-side discovery: paginate `GET /{version}/me/accounts?fields=name,access_token,tasks,instagram_business_account` with the user token, keeping Page tokens server-only. The selected Page ID must be in the just-discovered set. Resolve/validate its linked IG professional ID where present and the required Page tasks/scopes. Send only sanitized asset IDs/labels/eligibility to the selection UI. Recheck membership, session, one-time selection handle, provider asset and credential at selection time; store credential and `SocialAccount` mapping atomically. A partially authorized or failed selection remains disconnected.
5. Reconnect updates the **same** business/platform/provider account and rotates encrypted credential reference atomically; do not duplicate `SocialAccount` or discard scheduled/intended history. Disconnect is an explicit authorized action, makes the account nondispatchable, removes/revokes local usable credentials as supported, and records audit. Provider revocation/expiry sets a clear reauthorization-needed condition and never leaves a misleading `CONNECTED` state. Provider-side revocation is best effort and must not be represented as confirmed when Meta has not confirmed it.

## State and secret rules

`CONNECTING` is the OAuth attempt, not a new `SocialAccount` status. `CONNECTED` means selected provider ID, required scopes/tasks and server-side credential validated and stored. `DISCONNECTED` means no usable credential. Add `REAUTH_REQUIRED` only if needed to distinguish an established mapping whose credential is expired/revoked; otherwise model that condition in connection metadata and derive UI status. Keep provider/API errors on the attempt/audit rather than adding an `ERROR` account state for convenience. Revalidate usable credentials at actual dispatch in P6-03; a connection timestamp is not permanent proof.

Use server-only authenticated encryption (for example AES-256-GCM with random nonce and key ID/version) with a production secret supplied outside Git. Bind associated data to business/account/provider so ciphertext cannot be replayed across tenants. Fail closed when the key is unavailable; plan rotation/re-encryption without exposing plaintext. Only server-side credential resolution yields a token to the Meta client; the `PublishingAdapter` domain receives an opaque handle. Redact request URLs if they could include credentials, Meta payloads, HTTP errors, logs, UI responses and audit rows. Do not commit real app credentials or tokens.

## Meta documentation check (2026-09-25)

Meta's [official Graph API changelog](https://developers.facebook.com/docs/graph-api/changelog/) lists **v26.0 as the latest version, released July 29, 2026**. Target and explicitly pin `META_GRAPH_API_VERSION=v26.0` for P6-02 unless repository or official endpoint evidence requires another supported version; never use the unversioned default. Token exchange/expiry, App Review and production access requirements still need confirmation for the configured Meta app; no perpetual Page-token or automatic refresh guarantee is assumed.

Choose **Facebook Login + Instagram API with Facebook Login** because Ainetra needs Facebook Page and Instagram under one Meta connection. Meta's [official Facebook Login collection](https://www.postman.com/meta/instagram/folder/u4g5a2a/instagram-api-with-facebook-login) requires a Page-linked Instagram **professional** (Business/Creator) account and excludes personal accounts. [Instagram Login](https://www.postman.com/meta/instagram/folder/6raa77c/instagram-api-with-instagram-login) can connect a professional account without a linked Page, but uses different `instagram_business_*` scopes and is outside P6-02.

**P6-02 connection permissions — verified endpoint by endpoint:**

| Call/purpose | Minimum verified permission(s) |
| --- | --- |
| Discover manageable Pages, Page tokens and tasks with `GET /v26.0/me/accounts?fields=name,access_token,tasks,instagram_business_account` ([Meta request](https://www.postman.com/meta/instagram/request/0vuw3vk/get-access-tokens-of-pages-you-manage)) | `pages_show_list` for the Page list; `instagram_basic` for the linked IG field (per the [Page reference](https://developers.facebook.com/docs/instagram-api/reference/page/)) |
| Read/recheck the selected Page's linked IG professional ID with `GET /v26.0/{PAGE_ID}?fields=instagram_business_account` ([Meta Page reference](https://developers.facebook.com/docs/instagram-api/reference/page/)) | `instagram_basic` + `pages_show_list` |
| Validate the selected IG ID/allowed profile fields with `GET /v26.0/{IG_USER_ID}?fields=id,username` ([Meta IG User reference](https://developers.facebook.com/docs/instagram-api/reference/ig-user/)); verify selected Page ID/tasks again against server-side discovery | `instagram_basic` + `pages_read_engagement` for the IG User read; `pages_show_list` for Page discovery |

Thus the **baseline OAuth scope set is exactly `pages_show_list`, `instagram_basic`, `pages_read_engagement`** for the stated connection calls. The Meta IG Page/IG User references additionally say that when the person's Page role was granted through Business Manager, **one of `ads_read` or `ads_management` is also required**. This is conditional and broader than the baseline: do not request either by default. Verify the customer's role/path and current Meta app permission behavior before expanding scope; prefer the narrower approved route and surface an explicit unsupported/reauthorization result rather than marking the asset `CONNECTED` on partial access. Do not request the whole Postman collection's permission set.

**P6-03 publishing permissions (deferred):** `instagram_content_publish` for Instagram submission; verify the exact Facebook Page publishing permission(s), including `pages_manage_posts` where the selected endpoint requires it, in the P6-03 endpoint review. Seek incremental authorization/reauthorization when supported by the current Facebook Login setup; if not supported, document the consent and review tradeoff before expanding connection scopes. P6-02 does not request these or publish. **Future analytics/comment permissions (deferred):** insights, comment-management and messaging permissions such as `instagram_manage_insights` and `instagram_manage_comments` require their own endpoint review and are not part of P6-02 or P6-03. The collection-wide permission list is not a minimum connection list.

Development may use app-role/test users and eligible owned/test Pages while the app is in development mode, subject to Meta's current dashboard rules. Production onboarding of other businesses must **not** be declared ready from a local OAuth success: confirm current Live-mode eligibility, required permission access level/App Review, any Business Verification or access-verification prerequisites, redirect domain/policy/data-deletion setup, and provider production test with a non-role customer account. Record which are actually required by Meta for the chosen app configuration; do not generalize WhatsApp/Instagram Login requirements to this flow.
