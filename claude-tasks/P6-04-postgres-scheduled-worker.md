## Outcome and existing boundaries

Run a separately deployable, Ainetra-owned PostgreSQL poller that automatically publishes **due, current-version, already-approved** Instagram/Facebook scheduled posts using P6-03's immutable `PublishIntent`, `PublishAttempt`, Meta adapter and single state machine. Keep P6-03's three supported POST formats only. The existing `scheduleContentVariant` persists `ScheduledPost` but creates no intent; `requestPublishIntent` and `publishScheduledPostNow` require a user ID/membership and are currently invoked by the explicit button. The worker has no logged-in user. Extract narrowly shared, **server-only** intent-creation and dispatch cores so the user action retains `requireMembership` and the worker has a separate trusted process entrypoint, while both execute identical tenant/account/version/approval/snapshot/media/credential checks, Meta submission, CAS claim and evidence persistence. Do not pass a fake user ID, skip credential validation, or implement a second adapter path. `verifyMetaPublishingCredential` already permits a null audit actor for a background operation.

Reuse `src/features/publishing/{intent,submission,intent-state,adapter,meta-adapter,meta-result,snapshot,labels}.ts`, `src/features/publishing/service.ts`, `src/features/meta-connection/service.ts`, `src/lib/db.ts`, `prisma/schema.prisma`, `src/test/{publishing-foundation,native-meta-publishing}.test.ts`, `src/actions/publishing.ts`, and the current `ScheduledPost`/`PublishIntent`/`PublishAttempt` models. Proposed new files: focused `src/features/publishing/worker.ts`, `scripts/publishing-worker.ts` and `src/test/scheduled-publishing-worker.test.ts`; touch the shared modules, `package.json`, additive migration, environment example and deployment documentation only as needed. Do not redesign calendar/content UI: existing publication labels should reflect worker transitions; add a label only if an existing state cannot be shown.

## Eligibility and one authoritative claim

1. Use **absolute database timestamps** (`ScheduledPost.scheduledAt`, `PublishIntent.dueAt`, retry eligibility) and the database clock for due/claim decisions; never reinterpret persisted timestamps in the machine's local timezone. A deterministic injected clock or fixed database time must make tests repeatable.
2. Scan bounded, cursor-paginated due `ScheduledPost` rows with `status=SCHEDULED` and no generation-1 intent. Create/reuse the exact P6-01 immutable intent in a short Serializable transaction with the same approval, version, tenant, account/platform and media checks as the user path. Existing scheduled rows must participate; no destructive backfill. A unique `(scheduledPostId,generation)` race resolves to the same intent. Do not contact Meta before the intent is committed. Invalid/unsupported prerequisites are isolated and logged as closed categories, without fabricating an approved snapshot or stopping other tenants. Avoid starvation by advancing the scan cursor past an invalid row.
3. Poll due `PENDING` intents; poll `RETRY_WAIT` **only** when a persisted next-eligible time is due, the prior attempt has a definitive safe-to-retry rejection/pre-publication failure, and the retry budget remains. The poll query is advisory: the **existing P6-03 short Serializable/CAS claim** must be the only claim authority. Both button and worker must use it, keyed by the exact intent/attempt; a losing worker returns without a Meta call. No DB transaction spans a provider request. Use the existing lease/currentAttemptId/attempt-number fields, not a separate queue or global singleton.
4. Skip future work, active `IN_FLIGHT` leases, `UNKNOWN`, `PUBLISHED`, permanent `FAILED`, `CANCELLED` and `INVALIDATED`. On expired `IN_FLIGHT`, inspect durable attempt evidence and use the existing evidence-driven state machine. **Never infer non-publication from lease expiry alone.** Uncertain outcomes stay `UNKNOWN` for P6-05 and are never automatically resent.

## Retry budget and crash boundary

Set a small, explicit budget of **three total provider attempts** (initial plus at most two retries), with deterministic backoff of **60 seconds after the first safe rejection and 5 minutes after the second**, measured from the recorded outcome using the database clock. Add nullable `PublishIntent.nextAttemptAt` (indexed with state if needed) so `RETRY_WAIT` cannot spin every poll; derive the count from numbered `PublishAttempt` rows rather than duplicating it. Existing `RETRY_WAIT` rows with null `nextAttemptAt` are **not** automatically retried without verified safe evidence; user action or later explicit repair remains possible. A third definitive retryable rejection consumes the budget and transitions to terminal `FAILED` via the existing `RETRY_BUDGET_EXHAUSTED` evidence, with `ScheduledPost` status updated consistently and the attempt's original redacted rejection retained. Permanent/auth/permission refusals never retry. Do not turn a transport timeout, possible provider acceptance, ambiguous 5xx or `UNKNOWN` into `RETRY_WAIT`.

Crash cases must be explicit and testable: before claim, next poll can proceed; after claim but **provably before any publication call**, a later worker may safely recover only if a durable pre-call marker proves that boundary and the original worker cannot subsequently call Meta. Propose an additive nullable `PublishAttempt.publishCallStartedAt` (or a demonstrably equivalent durable marker) and a narrow callback/guard immediately before the first actual publish API call (FB `/feed` or `/photos`, IG `/media_publish`). The guard must CAS-check the same live lease/attempt and persist the marker **before** the call; if it fails, do not call Meta. IG container creation alone is not publication; preserve its existing container reference. An expired lease with an unmarked attempt may move through an explicit safe pre-publication evidence transition to `RETRY_WAIT` only if the adapter contract and CAS guard prove no publish call could have begun. A marked attempt, crash during call, accepted post before DB evidence write, lost response, uncertain DB write, or unprovable legacy attempt must become/remain `UNKNOWN`. A crash after writing the marker but before sending is conservatively `UNKNOWN`. A surviving old worker must not publish after its claim is revoked. A positive late provider result may be recorded on its attempt, but cannot overwrite newer intent evidence; P6-05 resolves it. Keep the P6-03 finalized-outcome behavior and immutable snapshot checks intact. If a smaller existing-field solution proves equally safe, document it in the implementation report; never weaken ambiguity rules for convenience.

## Process, deployment and observability

Use a bounded long-running poll loop with a small batch (for example 25 intents), configurable interval (default 15 seconds), per-job error isolation, bounded concurrent provider calls, database reconnect/backoff, and SIGTERM/SIGINT graceful shutdown that stops new claims, waits a bounded time for active calls, then exits; an interrupted/uncertain in-flight attempt is handled by the crash rules on restart. The worker does not depend on a Next request handler or browser session. A process/worker ID is for sanitized logs only; the attempt ID and CAS claim establish ownership. Log intent/attempt/state/category/duration and optionally tenant ID only under the existing policy; never tokens, encrypted values, signed media URLs, captions, raw provider bodies or media bytes. Emit useful counts for due, dispatched, safe retry, failed and reconciliation-required work. One broken tenant must not block another.

Provide an explicit `npm run worker:publishing` startup command for a **separate process** using the same deployed code, PostgreSQL and private media storage as the web app; no hosting vendor assumed. Suggested entrypoint: `node --conditions=react-server --import tsx ./scripts/publishing-worker.ts`, with `tsx` moved from dev-only to production dependencies **if this route is used**. The existing `server-only` package throws on ordinary Node imports and exposes an empty `react-server` condition: validate that this command and alias/generated Prisma imports really work from a production dependency install before choosing it. Do not leave a development-only command as the production contract. Document `DATABASE_URL`, `LOCAL_STORAGE_ROOT`, `META_APP_ID`, `META_APP_SECRET`, `META_GRAPH_API_VERSION`, `META_CREDENTIAL_KEY`/key rotation, `PUBLIC_APP_URL` and `MEDIA_DELIVERY_SECRET` as applicable; load them from the deployment secret store, never commit values. Run migrations before worker startup. A public HTTPS web origin and shared media storage are required for Instagram's signed-media fetch, even though the worker itself has no public listener.
