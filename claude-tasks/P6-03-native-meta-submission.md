## Exact outcome and formats

Implement a native Meta `PublishingAdapter` and one explicit **due-now** submission command for an already approved immutable `PublishIntent`. The user action may create/reuse that intent from the current approved `ScheduledPost` through `requestPublishIntent`, then dispatch it only when `dueAt <= now`; never auto-dispatch a future schedule. Ainetra PostgreSQL and the snapshot are authoritative; the provider call is an external side effect, not a new source of content truth.

Support only `ContentType.POST`: **Instagram single JPEG image + approved caption/CTA**, **Facebook Page text-only feed post**, and **Facebook Page single JPEG/PNG photo post + approved caption/CTA**. Instagram requires media; reject a text-only Instagram post. Reject missing, deleted, foreign-tenant or unsupported media before any provider call. Do not silently convert PNG/WebP to JPEG or mutate originals in P6-03. Compose caption and separate CTA deterministically from the frozen snapshot (the current preview displays them separately), validate the resulting provider text length, and never truncate or invent text. A previously accepted authentic derivative can be used if it is the snapshot's selected `MediaAsset`; no implicit replacement or new approval. Explicitly defer Reel/video, Story, Carousel/multi-image, Facebook video, WebP/other unsupported files, tagging, location and branded-content extras. Existing video ingestion checks only a container signature, not codec/dimensions, so video requires later bounded validation/processing and asynchronous readiness handling.

## Official Meta checks (2026-09-26)

- [Graph API changelog](https://developers.facebook.com/docs/graph-api/changelog/): latest v26.0 (July 29, 2026); reuse P6-02's pinned `META_GRAPH_API_VERSION=v26.0` unless current official endpoint evidence requires a different supported version.
- [Instagram content publishing guide](https://developers.facebook.com/docs/instagram-api/guides/content-publishing/) and [IG User Media reference](https://developers.facebook.com/docs/instagram-api/reference/ig-user/media/): Facebook Login uses a Page access token with `instagram_basic`, `instagram_content_publish`, `pages_read_engagement`; Business Manager-granted Page roles may additionally need `ads_read` or `ads_management` as documented. P6-02's `pages_show_list` remains needed for Page connection/discovery. Do **not** infer publish permission from connection scopes: add an explicit user-facing reauthorization path for `instagram_content_publish` if Meta's current incremental authorization permits it; if not, require an explicit consent/review decision before widening requested scopes. The linked Page must allow a publishing task and may require Page Publishing Authorization (PPA). Instagram single-image flow: `POST /v26.0/{IG_USER_ID}/media` with `image_url`/caption → persist container ID → check `GET /v26.0/{CONTAINER_ID}?fields=status_code` when needed → `POST /v26.0/{IG_USER_ID}/media_publish` with `creation_id` → require returned IG media ID for `PUBLISHED`. Container creation or `FINISHED` is **not** publication. Container states include `IN_PROGRESS`, `FINISHED`, `ERROR`, `EXPIRED`, `PUBLISHED`; an ambiguous publish response stays `UNKNOWN` pending P6-05 reconciliation. Meta fetches `image_url` itself; the URL must be publicly reachable at fetch time. JPEG only, at most 8 MB, aspect ratio 4:5–1.91:1, width 320–1440 px (Meta may scale), sRGB; validate local bytes/metadata without altering the approved asset. The guide states 100 API-published IG posts per moving 24 hours and provides `GET /{IG_USER_ID}/content_publishing_limit`; handle the limit explicitly rather than blind retry.
- [Facebook Page feed reference](https://developers.facebook.com/docs/graph-api/reference/page/feed/) and [Page photos reference](https://developers.facebook.com/docs/graph-api/reference/page/photos/): Page access token, Page `CREATE_CONTENT` task, `pages_manage_posts`, `pages_read_engagement`, `pages_show_list`. Text-only: `POST /v26.0/{PAGE_ID}/feed` with `message`, `published=true`; require returned post ID. Single photo: `POST /v26.0/{PAGE_ID}/photos` with `source` multipart bytes, `caption`, `published=true`; require returned post/photo evidence (`post_id` where provided). Photos support JPEG/PNG and at most 10 MB. The broader [Page posts guide](https://developers.facebook.com/docs/pages-api/posts/) lists extra permissions for broader interactions; do not request its additional `pages_manage_engagement`, `pages_read_user_engagement` or `publish_video` permissions for these two calls without endpoint evidence.
- [Graph error guide](https://developers.facebook.com/docs/graph-api/guides/error-handling/) and [Instagram error codes](https://developers.facebook.com/docs/instagram-api/reference/error-codes/): parse numeric code/subcode and provider retry signals into a **closed redacted** classification. Token expiry/revocation (e.g. 190) and missing permission (200–299) require reconnect/authorization; invalid input/media is permanent; documented throttle/transient errors are retryable **only when provider rejection is definite**. A timeout, lost response, connection reset or uncertain 5xx after a publish call is `UNKNOWN`, not safe retry. Never persist raw provider message, token, URL with credential, caption or media bytes as diagnostics.

The chosen publish references do not document a provider idempotency-key guarantee or authoritative lookup by Ainetra's key. Advertise `supportsIdempotencyLookup=false`; do not claim exactly-once provider delivery. Known IG container IDs or confirmed remote post IDs are useful reconciliation references, but their absence after an ambiguous call cannot justify another publish. Confirm any optional lookup capability only from official endpoint evidence.

## Media delivery and modules

Reuse `PublishSnapshotV1` (caption/CTA, selected media ID, `storageKey`, origin and derivative lineage), `storage.get`, `checkPublishIntentDispatchable`, `planIntentTransition`/`evidenceFromSubmitOutcome`, `getMetaAccountConnection` and `resolveMetaAccessToken`. The P6-02 Graph client already limits time/response size and redacts errors; extend/reuse it for publishing where sensible. Add focused server-only files under `src/features/publishing/` for Meta adapter, submission service and provider-result normalization; minimally extend the schema/migration for durable claim/attempt identity and **separate** IG container vs final post references only if existing fields cannot safely hold both. Add a thin due-now server action/route and minimal status labels in the existing content/calendar surface; no UI redesign or browser-supplied provider target.

Current `StorageProvider` is private local read/write/delete and offers **no signed URL**. For Instagram, add the smallest Ainetra-owned HTTPS media-delivery capability for the exact frozen asset, such as an expiring signed fetch URL backed by `storage.get`; make it reachable to Meta without Ainetra cookies, bound to intent/business/media/key, read-only, time-limited long enough for Meta fetch, revocable/expiring, with correct JPEG content type and bounded response. Do not publish the bucket or original permanently. Treat URL signatures as secrets: redact route/proxy logs and errors, use no third-party redirects, and test expiry, tampering and cross-tenant access. Production needs a publicly reachable HTTPS origin; localhost alone cannot pass live IG publishing. Facebook photo uses Meta's documented multipart `source` upload directly from the frozen private bytes, so no public URL is needed there. Never expose Meta credentials to the media endpoint or client. Preserve original media and any accepted derivative lineage.

## Submission, state and duplicate safety

1. Authorize the acting user for `intent.businessId`; derive account, platform, provider IDs and payload from the persisted intent/snapshot only. Recheck due time, current approval/version, snapshot hash, media tenant/storage identity, connection/account mapping, and P6-03 publish scopes/Page task. Validate the credential immediately before provider work using a server-only dispatch path through the P6-02 boundary; `SocialAccount.status` alone is insufficient. Keep authorization separate from the P6-02 OWNER-only settings action.
2. In one short Serializable/CAS transaction, revalidate dispatchability and atomically claim `PENDING` (or a **definitively** retryable `RETRY_WAIT`) as `IN_FLIGHT`, set a bounded lease, and create one numbered `PublishAttempt` tied to that claim. Only the winning caller proceeds; duplicate clicks/concurrent requests return the existing state/attempt without a second Meta call. Keep the existing state machine authoritative; do not introduce a parallel one. No DB transaction spans a Meta request. Recheck the claim/source before the first external call; source invalidation while in flight becomes `UNKNOWN` as P6-01 requires.
3. `prepareMedia` and `submit` use the immutable snapshot and opaque `CredentialHandle`. Persist an IG container ID **before** calling `media_publish`; persist final Meta post/media ID, provider request ID when available, adapter key/version, timestamps, sanitized diagnostics and outcome on the attempt. Save the attempt outcome and `PublishIntent` evidence/transition atomically or with compare-and-set against the exact claimed attempt; stale workers cannot overwrite newer evidence. A positive Meta post/media ID permits `PUBLISHED`; a definite permanent refusal permits `FAILED`; a definite transient refusal permits `RETRY_WAIT` but P6-03 does not run a retry worker. `PENDING`/`IN_FLIGHT`/`UNKNOWN` remain visible as such. On process death after submission or lease expiry, mark/recover as `UNKNOWN`, never auto-resend.
4. Meta publish calls shown above have no documented native idempotency key. Ainetra's stable intent key deduplicates **local** action and attempt creation; it does not make Meta exactly-once. After a timeout, ambiguous 5xx or crash after Meta accepted, retain `UNKNOWN` and any known container/post reference; **do not retry UNKNOWN**. P6-05 owns provider reconciliation/operator resolution. No provider response body, timeout or container-ready status may be interpreted as a published post without positive final evidence.

## Tests, live validation, non-goals

Focused deterministic tests with a fake Meta client/storage/clock: current vs stale approval/version; immutable snapshot payload despite later edits; cross-tenant intent/account/media or forged provider ID; missing/disconnected/reauth-required/expired/under-scoped credential; due-now vs future schedule; unsupported media/format/size/aspect; CTA length; signed fetch capability expiry/tamper/tenant; FB text/photo and IG JPEG endpoint ordering; IG container ID persisted before publish; positive post ID vs container-only; definite permanent/transient vs ambiguous timeout/5xx; duplicate click/concurrent claim; crash/expired lease/UNKNOWN no resend; no secrets in logs/errors/browser; P6-01/P6-02 regression. Codex runs targeted tests, then full suite, lint, build, audit and migration status under the existing QA loop.

**Live Meta checklist (not claimed without credentials):** configured Live-mode Meta app v26.0, approved publish permissions/non-role customer, suitable Page task/PPA and IG professional linkage; HTTPS callback and public short-lived media endpoint; real JPEG meeting Meta specs; one IG image and one FB text/photo test account; verify returned remote IDs and visible posts; duplicate-click and lost-response/reauthorization observation; inspect rate-limit/error responses and confirm no token/media URL leakage. Fake-client tests alone do not establish live publishing readiness.

Non-goals: scheduled/cron worker, automatic retry budget, general reconciliation/cancel/reschedule, Reels/videos/stories/carousels, FFmpeg, tusd, imgproxy, Postiz, BullMQ, TikTok, analytics, comments/messages, Phase 7, Sales, Serve, Control.
